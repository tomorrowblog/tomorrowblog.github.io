零成本搭建永久图床！Github+PicGo保姆级教程，自媒体人效率翻倍秘籍

发表于2026-11-08|更新于2026-11-08|实用教程
|总字数:1908|阅读时长:8 分钟|浏览量:

写公众号、博客或技术文档时，最麻烦的环节之一就是处理图片：截图散落在桌面，文章搬到另一个平台后图片失效，换电脑又要重新整理。用 GitHub 仓库 + PicGo 可以搭一套零成本、自己掌控的图片管理流程。

先说清楚：这里的“永久”是指图片存放在自己的仓库里，可以随时备份和迁移，不代表 GitHub 承诺永久免费或链接永远不会失效。GitHub 也不是专业 CDN，中国大陆访问速度和稳定性取决于网络环境。适合个人博客、低流量内容站和日常写作；商业高流量站点仍建议使用对象存储加 CDN。

这套方案适合谁？

场景是否适合说明
个人博客、技术文档适合图片量不大，维护成本低
公众号、知乎等自媒体配图适合先在本地保存，再按平台上传
团队共享素材库谨慎需要额外管理权限和文件命名
高流量商业网站不建议GitHub 不适合作为正式 CDN
身份证、合同等敏感图片禁止公开仓库中的文件可能被任何人访问

准备工作

你需要：

  1. 一个 GitHub 账号；
  2. 安装 PicGo；
  3. 准备一个专门存放图片的公开仓库；
  4. 一个只拥有该仓库读写权限的 GitHub Token。

不要把 Token 写进文章、截图或代码仓库。Token 一旦泄露，应立即删除并重新生成。

第一步：创建图片仓库

登录 GitHub，点击右上角 + → New repository：

  • Repository name：例如 blog-images；
  • Visibility：选择 Public；
  • 勾选 Add a README file；
  • 点击 Create repository。

公开仓库是必须的，否则普通图片链接无法直接访问。仓库名称可以自定义，但建议把用途写清楚，例如：

这样以后图片多了也容易查找和迁移。

第二步：创建最小权限 Token

进入 GitHub：

Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token

按下面设置：

  • Token name：picgo-blog-images
  • Expiration：按自己的习惯选择 90 天或 1 年；
  • Resource owner：选择自己的账号；
  • Repository access：Only select repositories；
  • 只选择刚才创建的 blog-images；
  • Repository permissions → Contents：Read and write。

其他权限不需要开启。点击生成后，GitHub 只会显示一次 Token，先复制到安全的位置。

建议定期更换 Token。所谓“零成本”不等于“零维护”，Token 过期后 PicGo 会提示上传失败，重新生成并替换即可。

第三步：配置 PicGo 的 GitHub 图床

打开 PicGo，进入 图床设置 → GitHub，填写：

配置项示例
仓库名yourname/blog-images
分支名main
Token刚才生成的 GitHub Token
存储路径posts/2026/11/
自定义域名https://cdn.jsdelivr.net/gh/yourname/blog-images@main

注意把 yourname 换成自己的 GitHub 用户名。仓库名必须写成“用户名/仓库名”，不能只写 blog-images。

保存后，把 GitHub 设为默认图床。之后在 PicGo 上传区拖入一张图片，等待上传完成，复制生成的 Markdown 链接。

第四步：把上传流程接进写作工具

PicGo 支持命令行和多种编辑器集成。以 Typora 为例，可以在图片设置中选择 PicGo 作为上传服务，并设置 PicGo 程序路径。配置完成后，插入本地图片时可以自动上传并替换成网络链接。

建议同时开启两个习惯：

  1. 上传前先压缩图片；
  2. 上传后保留一份本地原图。

图片上传成功不代表原图可以删除。GitHub 仓库只是副本，账号异常、误删仓库或平台策略变化都可能影响访问。重要图片至少保留本地备份，最好再同步到移动硬盘或私有网盘。

第五步：让图片体积更小

图床是否好用，很大程度取决于图片体积。建议：

  • 截图统一转为 WebP 或高质量 JPEG；
  • 长边控制在 1600～2000 像素；
  • 单张图片尽量控制在 500 KB 以内；
  • 照片质量设为 75～85；
  • 文件名使用英文、数字和短横线，避免空格和特殊符号。

不要上传几十 MB 的原图，也不要为了“高清”把所有截图都保存成 PNG。仓库越大，克隆、备份和页面加载都会变慢。

常见问题

上传成功但图片打不开

依次检查：

  1. 仓库是否为 Public；
  2. 分支名是否与仓库实际分支一致；
  3. 自定义域名是否包含用户名和仓库名；
  4. 文件是否真的出现在 GitHub 仓库中；
  5. jsDelivr 是否有缓存延迟。

刚上传的图片如果通过 jsDelivr 访问不到，可以先打开 GitHub 仓库确认文件存在，再等待几分钟或换用原始地址测试。

提示 403 或 Permission denied

通常是 Token 权限不足或已经过期。重新检查：

  • Token 是否只授权了图片仓库；
  • Contents 权限是否为 Read and write；
  • PicGo 中是否粘贴了完整 Token；
  • Token 是否已被删除或过期。

图片在国内加载慢

这是 GitHub 图床最常见的限制。可以尝试：

  • 压缩图片，减少首屏加载体积；
  • 使用稳定的 CDN 域名；
  • 给博客图片增加懒加载；
  • 对高访问量图片改用对象存储或自建图床。

如果图片是商业网站的核心资源，不要把 GitHub 当作唯一方案。

如何避免图片丢失？

至少做三层保护：

  1. GitHub 仓库保存一份；
  2. 本地保留原始图片；
  3. 定期把仓库克隆到另一块硬盘或私有备份位置。

Git 仓库可以恢复历史版本，但前提是仓库还在、账号还能登录。不要把“云端有文件”误解成“永远不需要备份”。

最终检查清单

  • 创建了公开的图片仓库；
  • Token 只授权图片仓库的 Contents 读写权限；
  • PicGo 能成功上传并生成 Markdown 链接；
  • 图片链接可以在无登录状态下打开；
  • 已设置图片压缩和统一命名规则；
  • 本地保留了原图备份；
  • 没有上传身份证、合同、密码等敏感图片。

总结

GitHub + PicGo 的价值不只是“免费”，更重要的是流程简单、文件可控、迁移方便。对个人博客和日常写作来说，这是一套成本很低的起步方案。

但要记住：GitHub 不是专业图床，免费也不等于永久。把图片掌握在自己手里、做好压缩和备份，再根据流量选择合适的 CDN，才是更稳妥的长期方案。
